# Release and signing

This document describes how Fluxa becomes installable packages, what is signed,
what is not, and how to verify each artifact yourself. It deliberately separates
**test builds** from **release builds**: only the latter are signed, and only the
Android artifact is signed today.

## Version and identifier sources

| Field | Source of truth | Propagated to |
| --- | --- | --- |
| version | `package.json` | `android/version.properties`, `android/app/src/main/res/values/strings.xml`, artifact filenames, build manifest |
| versionCode | derived: `major*10000 + minor*100 + patch` | `android/version.properties` (0.2.0 → 200) |
| app name | `build.productName` = `Fluxa` | Electron `productName`, Android `app_name`, window title |
| app id | `build.appId` / `capacitor.config.ts` = `com.fluxa.transfer` | Electron `appId`, `CFBundleIdentifier`, Android `applicationId` |

Bump with:

```bash
npm version patch      # or minor/major — writes package.json and creates a tag
node scripts/sync-version.mjs        # verifies every target agrees
node scripts/sync-version.mjs --check # CI-safe: exits non-zero if out of sync
```

`versionCode` is monotonic, so Play Console will accept successive uploads
(0.2.0 → 200, 0.2.1 → 201, 0.3.0 → 300).

## Verifying an artifact

```bash
# hashes
sha256sum -c SHA256SUMS

# Android: signature and identity
apksigner verify --verbose --print-certs Fluxa-0.2.0-release.apk
aapt2 dump badging Fluxa-0.2.0-release.apk | head -3     # package/version/label

# Windows: version resource inside the exe
node -e "const s=require('fs').readFileSync('release/win-unpacked/Fluxa.exe').toString('latin1'); console.log(s.includes('0\u0000.\u00002\u0000.\u00000'))"

# macOS: bundle identity
/usr/libexec/PlistBuddy -c 'Print :CFBundleIdentifier' Fluxa.app/Contents/Info.plist

# Linux deb metadata
dpkg-deb --info Fluxa-0.2.0-linux-amd64.deb | head -12

# Electron running the packaged app, not a dev server
npx playwright@1.64 electron   # or e2e-desktop/ with executablePath → release/linux-unpacked/fluxa
```

## Linux

Built with electron-builder (`npm run dist:linux`). The AppImage is portable; the
deb installs to `/opt/Fluxa` with a `/usr/bin/fluxa` symlink and a desktop entry.

**Not signed.** There is no GPG key, no `.deb` repository metadata and no
AppImage signature. Distributing these to other people means asking them to
bypass a warning or to verify the SHA-256 manually.

Optional signing path (requires you to own a GPG key):

```bash
gpg --detach-sign --armor release/Fluxa-0.2.0-linux-x86_64.AppImage
dpkg-sig --sign builder release/Fluxa-0.2.0-linux-amd64.deb
```

## Windows

Built with electron-builder NSIS + portable targets. **Unsigned**: there is no
Authenticode certificate, so SmartScreen will warn until the binary gathers
reputation or is signed.

To sign, obtain an EV/OV code-signing certificate and provide it to
electron-builder through environment variables (never in the repo):

```bash
export CSC_LINK=/secure/path/fluxa.pfx     # or base64 of the pfx
export CSC_KEY_PASSWORD='…'
npm run dist:win
```

CI equivalent: add `CSC_LINK` and `CSC_KEY_PASSWORD` as project environment
variables; `build-windows` will use them automatically.

On a Linux host, electron-builder needs `wine` and `wine32` (i386) to stamp the
executable; CI uses a real Windows machine instead, which avoids that shim.

## macOS

A `.app` and a `.zip` can be produced on Linux (unsigned, unusable for normal
distribution because of Gatekeeper). A `.dmg` needs macOS (`hdiutil`), which is
why the CI `build-macos` job runs on a macOS executor.

Real distribution requires an Apple Developer Program membership ($99/yr):

1. Create a **Developer ID Application** certificate; export it as `.p12`.
2. Put it in CI as `CSC_LINK` (base64) and `CSC_KEY_PASSWORD`.
3. Notarise: electron-builder's `notarize` option with `APPLE_ID`,
   `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID`, or `notarytool` after the
   build.
4. Staple: `xcrun stapler staple Fluxa.app`.

Until all four exist, macOS builds stay **unsigned and un-notarisable**, and the
manifest reports them that way.

## Android

The release key was generated in this workspace with:

```bash
keytool -genkeypair -v -keystore fluxa-release.keystore -alias fluxa \
  -keyalg RSA -keysize 4096 -validity 10950 \
  -storetype PKCS12 -dname "CN=Fluxa, OU=Fluxa Releases, O=Fluxa, L=Abuja, ST=FCT, C=NG"
```

Build-time wiring: `android/app/build.gradle` reads `android/keystore.properties`
(absolute path + passwords) and only configures the release signing config when
that file exists. Locally:

```bash
cat > android/keystore.properties <<EOF
storeFile=/absolute/path/fluxa-release.keystore
storePassword=…
keyAlias=fluxa
keyPassword=…
EOF
chmod 600 android/keystore.properties
node scripts/sync-android.mjs
(cd android && ./gradlew assembleRelease bundleRelease)
```

`keystore.properties` is git-ignored and must stay that way — losing the keystore
means you can never update an app installed from it (and Play Console requires
the **same** key for every upload unless you use Play App Signing with an upload
key).

In CI the key arrives as `FLUXA_ANDROID_KEYSTORE_B64` (base64 of the keystore)
plus `FLUXA_ANDROID_STORE_PASSWORD`, `FLUXA_ANDROID_KEY_ALIAS` and
`FLUXA_ANDROID_KEY_PASSWORD`. The job writes it to `$HOME` outside the repo,
chmods 600, and deletes it in an `always` step. Without the variable the job
produces an **unsigned** APK and says so.

Installing the APK:

```bash
adb install -r Fluxa-0.2.0-release.apk        # device with USB debugging
# or copy to the phone, enable "install unknown apps" for the file manager
```

Play Store: create the app in Play Console, enrol in Play App Signing, upload the
`.aab` to an internal testing track. That action is **not** automated and must
not be until the account, listing, privacy policy and content rating exist.

Android limitations that are real, not cosmetic:

* mDNS discovery is unavailable in the WebView, so Android pairs by code/QR only.
* Received files are written through the app's own storage; the system Downloads
  folder needs a MediaStore/SAF integration that is not implemented yet.
* Cleartext HTTP to a local signalling server is permitted by
  `res/xml/network_security_config.xml` (documented there); a public deployment
  should use HTTPS and a strict config.

## iOS

Not built. Requirements to build one honestly:

* a macOS machine or CI macOS executor with Xcode,
* an Apple Developer account (bundle id `com.fluxa.transfer` must be registered),
* provisioning profiles for development/ad-hoc/App Store,
* `npx cap add ios` and a WebRTC-capable WKWebView check.

Until that exists, the platform matrix says ❌ rather than shipping something
unverified.

## Release checklist

1. `npm ci && npm run check && npm test && npm run test:e2e && npm run test:desktop`
2. `node scripts/sync-version.mjs --check` (fails if a target drifted)
3. `git tag v0.2.0 && git push origin v0.2.0` → the `release` workflow runs the
   full test gate and every platform build, then waits for approval
4. Approve `hold-for-release` in CircleCI
5. Download `release/` and `android-*/` artifacts from the CircleCI job; check
   `build-manifest.json` and `SHA256SUMS`
6. Review the **draft** GitHub release, add the supported-platform table, publish
   manually
7. Keep the Android keystore and its passwords offline, in a password manager
